# Voice Architecture

## Overview

This document describes the original voice-layer split (LiveKit transport, orchestration, Interview Intelligence). Runtime startup commands, current STT/TTS providers, and the LiveKit Agents worker entrypoint are in the root [README.md](../../README.md).

`MockInterviewBridge` remains a test double only. The production voice path uses `InterviewIntelligenceBridge` in the API process and `HttpInterviewBridge` in `python -m app.agents.worker`.

## Pipeline

```
Candidate Audio (microphone)
        ↓
    LiveKit (real-time audio transport)
        ↓
    Pipecat (orchestration layer)
        ↓
    STT Provider (speech → text)
        ↓
    Interview Intelligence (Faizan's module — evaluation, adaptive difficulty)
        ↓
    TTS Provider (text → speech)
        ↓
    LiveKit (real-time audio transport)
        ↓
Candidate Audio (speaker)
```

## Adaptive Interview Loop

```
Question (generated by Interview Intelligence)
        ↓
Candidate Answer (transcribed by STT)
        ↓
Evaluation (scored by Interview Intelligence)
        ↓
Difficulty Adjustment (determined by Interview Intelligence)
        ↓
Next Question
```

## Architecture Principles

### Provider Agnosticism

STT and TTS integrations use an abstract base class pattern:

```
STTProvider (abstract)
├── MockSTTProvider       ← Day 1 (testing)
├── WhisperSTTProvider    ← Future
├── GoogleSTTProvider     ← Future
└── DeepgramSTTProvider   ← Future

TTSProvider (abstract)
├── MockTTSProvider       ← Day 1 (testing)
├── ElevenLabsTTSProvider ← Future
├── GoogleTTSProvider     ← Future
└── AzureTTSProvider      ← Future
```

New providers are registered via a factory pattern. No code changes are needed outside the provider implementation and factory registration.

### Interview Bridge

Pipecat communicates with Interview Intelligence through a clean `InterviewBridge` interface:

```python
class InterviewBridge:
    async process_candidate_response(text, session_id) -> dict
    async get_next_question(session_id) -> Optional[str]
    async evaluate_answer(text, question_id, session_id) -> dict
```

This allows Faizan to implement the intelligence layer independently. A `MockInterviewBridge` is provided for testing the pipeline without real AI.

### Pipecat Is NOT the AI Brain

Pipecat is the **orchestration layer**. It coordinates the flow between STT, Interview Intelligence, and TTS. It does not:

- Generate questions
- Evaluate answers
- Adjust difficulty
- Make assessment decisions

All intelligence comes from the Interview Intelligence module (Faizan's responsibility).

### LiveKit Is the Transport Layer

LiveKit handles:

- WebRTC session establishment
- Real-time audio streaming
- Room management
- Participant authentication (token generation)

LiveKit does NOT process or understand audio content.

## Current Limitations (Day 1)

- All STT/TTS providers are mock implementations
- LiveKit SDK is not yet integrated (configuration foundation only)
- Pipecat pipeline is a structural foundation, not yet processing real audio
- Interview Intelligence is mocked via InterviewBridge
- Sessions are stored in-memory (no database persistence)
- No authentication on voice API endpoints
- No real-time WebSocket communication yet

## Future Integration Points

1. **Real STT Provider**: Implement `STTProvider` abstract class with chosen provider SDK
2. **Real TTS Provider**: Implement `TTSProvider` abstract class with chosen provider SDK
3. **LiveKit SDK**: Integrate `livekit-api` package for room/token management
4. **Pipecat SDK**: Integrate `pipecat-ai` for real pipeline orchestration
5. **Interview Intelligence**: Faizan implements `InterviewBridge` with real AI logic
6. **Database**: Replace in-memory session storage with persistent database
7. **WebSocket**: Add real-time session updates via WebSocket
